Candidate A

Four storage directories, four owners, one leaked manifest entry

Strong

Modules involved: app-shell · roster · homework · parents · export-backup

Problem

Four modules write app-internal files, and the directory conventions live on three different cards — photo-storage (roster), attachment-storage (homework), parents' pdfstore/ dir (owned by nobody). Meanwhile the single FileProvider entry sits in app-shell's setup and must enumerate every module's directory: "file_paths covering the photo, attachment, and export/PDF directories."

  • app-shell's implementation hardcodes every storage module's internals — adding a fourth dir ripples into app-shell, and its setup step literally tells builders to "coordinate".
  • parents' PDF directory is referenced by app-shell's file_paths but documented on no card.
  • export-backup's backup zip must consume two storage conventions and know a third exists.

Solution

Promote storage to one interface: an internal-storage seam owned by core-data (which already owns "everything persisted" — IDs, timestamps, repositories). One root directory, one file_paths entry, subdirs handed to consumers by name. Feature modules consume internal-storage and name their subdir; export-backup's zip consumes one interface; app-shell's FileProvider setup references only the root.

Benefits

  • Locality: "where does data live" concentrates in one card.
  • Leverage: five modules get path + FileProvider correctness from one interface.
  • Build verification: no cross-owner chat for a manifest entry; backup verifies through one consumed interface.
  • Deletion test: passes — core-data absorbs a real convention; complexity concentrates, doesn't move.

Candidate B

"Attendance %" is computed by everyone except attendance

Worth exploring

Modules involved: attendance · roster · export-backup

Problem

The meaning of an attendance percentage is implemented twice, by two modules that don't own attendance: roster's student page renders a per-student %, and export-backup's summarize/ computes monthly per-student/class figures. The attendance module — which defines statuses, Late/Excused, the optional period — computes neither.

The README already flags the formula as a client question ("does Late count as present?"). When that answer lands, three cards change instead of one, and two implementations must be found and fixed in lockstep. That's decision-risk with no owner.

Solution

Deepen attendance to also produce attendance-summaries — pure aggregation over data-repositories for a (student | class, date range). roster's student page and export-backup's writers both become renderers of one model; export-backup drops its summarize/ folder.

Benefits

  • One formula, one test surface — a client answer is a one-card redo.
  • roster stops knowing attendance math; export-backup shrinks toward its interface (formats + SAF).
  • Consumers verify through Connections alone: counts in, percentages out.

Honest cost: the duplication today is two small functions — this buys locality of a decision the README itself marks UNKNOWN.

Candidate C

PdfDocument page layout would be written twice

Worth exploring

Modules involved: parents · export-backup

Problem

Both cards independently implement framework PdfDocument layout: parents renders announcement paragraphs with StaticLayout, export-backup's writers/ renders summary pages the same way. Pagination — flowing text across A4 pages, headers/footers, "does this paragraph fit" — is the nontrivial half, and it would exist twice, drifting (parents gets a pagination fix export-backup never hears about).

Solution

One deep seam: a pdf-layout helper (blocks of text/table in → paged PdfDocument out) owned by one module, consumed by both. Where it lives is a grill question — beside internal-storage in core-data (candidate A), or app-shell's file-output side.

Benefits

  • Pagination fixed once; both PDFs inherit fixes.
  • Small, verifiable interface: content blocks in, paged PDF out.
  • If A has landed, this slots next to internal-storage naturally — one "file output" owner.

Prototype may honestly survive duplication — rate it against how fancy the PDFs need to be at Phase 0.

Candidate D

export-backup does two jobs

Speculative

Modules involved: export-backup (split)

Problem

Reporting (summaries → CSV/Excel/PDF for the client) and device backup (checkpoint hook, zip, validated restore) share one card but share nothing else: different consumers, different risk profiles — restore is the app's only destructive operation. Backup churn (WAL handling, marker format) edits a card whose other half is about classroom reports.

Solution & honest cost

Split into reports (screen, writers, SAF export) and backup (archive, restore, checkpoint seam) — the destructive capability gets its own explicit card and build verification.

Cost: two cards, two screen sections wired separately, SAF/ViewModel boilerplate duplicated. And if candidate A lands, backup's storage dependency collapses to one consumed interface — shrinking this split's value further.

Top recommendation

Candidate A first. It's the only Strong finding: the leak is already visible in four cards' setup steps and build notes ("coordinate with the app-shell owner"), it strands one undocumented directory, and it makes the backup module consume two interfaces where one would do. Fixing it removes a coordination tax from the entire build before any code exists.

Then B — small, and it pins down a decision the README itself flags as unknown, before two implementations fork on it. C is worth 15 minutes of grill once A's owner is known; D only if, after A, backup still feels crowded on its card.
